# سناریوی جامع بازوی خرید — صفر تا صد (سند مرجع)

> پروندهٔ بازوی خرید — آی مچ. این سند، مرجع تصمیم‌های محصولی فرایند خرید است؛
> هر تغییر آیندهٔ بازوی خرید باید با همین سند هم‌راستا شود.
> وضعیت‌ها: ✅ پیاده‌شده · 🟡 پیاده‌شده با ساده‌سازی آگاهانه · 🔨 در همین نسخه پیاده می‌شود · ⏳ آینده

## نقش‌ها
- **خریدار** (مالک بازوی خرید؛ مثلاً سوپرمارکت)
- **تامین‌کننده** (فروشندهٔ عضو؛ مثلاً شرکت پخش)
- **آی مچ** (اعلان‌ها، گیت‌ها، ثبت وضعیت‌ها)

## قاعدهٔ طلایی تماس
ملاک هر شماره‌ای در کل فرایند، **موبایل ثبت‌نام شخص** است (نه شمارهٔ کسب‌وکار)؛
شمارهٔ کسب‌وکار فقط «دکمهٔ دوم» است. دکمهٔ تماس همیشه در دسترس است — حتی روی ردیف‌های در انتظار/ردشده —
چون مذاکرهٔ انسانی قلب آی مچ است. ✅

---

## فاز ۱ — ساخت بازوی خرید (خریدار)
1. خریدار از `/inquiries/new` با انتخاب کسب‌وکار، بازوی خرید می‌سازد: عنوان، توضیح، استان/شهر، تگ‌ها. ✅
2. تنظیمات (تب تنظیمات): آدرس اختصاصی (اسلاگ)، عمومی/خصوصی، «پذیرش قیمت برای خریدهای غیرفوری»،
   «نمایش شمارهٔ تماس من»، شرایط ارسال/پرداخت، واحدهای منتخب. ✅
3. وضعیت اولیه: `open` = «در حال قیمت‌گیری». ✅
4. کارت ویزیت بازو (استودیو) + کیت اشتراک‌گذاری (مخاطبین تلفن/واتساپ/تلگرام/QR) برای انتشار ویروسی. ✅

## فاز ۲ — اقلام خرید (خریدار)
1. افزودن قلم‌به‌قلم: انتخاب از مرجع کالا، مقدار + واحد (مرجع واحد + واحدهای من)، برند/مشخصات/یادداشت/لینک. ✅
2. **شروع قیمت‌گیری قلم**: تیک «فوری» + مهلت ارسال قیمت به ساعت → تامین‌کننده‌ها تا مهلت فرصت دارند. ✅
   - 🟡 ساده‌سازی فعلی: مهلت، «مهلت گروهی کل بازو» است (شروع قیمت‌گیری هر قلم، مهلت بازو را می‌نویسد). قابل قبول — این سادگی برای کاربر بازار مبهم‌ترین نقطهٔ نیمه‌پیاده را حذف می‌کند.
3. قلمِ غیرفوری فقط وقتی به تامین‌کننده دیده می‌شود که «پذیرش قیمت غیرفوری» روشن باشد. ✅
4. ویرایش/حذف قلم؛ توقف قیمت‌گیری هر قلم. ✅

## فاز ۳ — شبکه‌سازی: بازوی خرید ↔ بازوی فروش تامین‌کننده
> قانون: «همهٔ ارتباطات = اعلام خرید + بازوی فروش فروش». عضویت همیشه دوطرفه sync می‌شود. ✅

1. **بازوی عمومی**: هر تامین‌کننده از بازار/جست‌وجو/لینک می‌رسد؛ **بازوی خصوصی**: فقط اعضای تاییدشده قیمت می‌دهند (گیت بک). ✅
2. **درخواست همکاری تامین‌کننده** (از صفحهٔ عمومی، با انتخاب بازوی فروش فروشش): `pending` →
   تایید با خریدار؛ رد → «درخواست رد شده» + حذف. ✅
3. **دعوت خریدار** (سرچ استان/شهر/صنف + مخاطبین موبایل): `pending` = «در انتظار پذیرش تامین‌کننده» →
   تایید با تامین‌کننده؛ رد → «درخواست رد شده» + دکمهٔ حذف. ✅
4. **تماس همه‌جا**: دکمهٔ تماس روی همهٔ ردیف‌ها (در انتظار/فعال/ردشده) برای پیگیری انسانی. ✅
5. فیلترهای همشهری/هم‌صنفی در جست‌وجوی تامین‌کننده و اول بودن «واحدهای من» و «واحدهای بازو» در فرم‌ها. ✅
6. اعلان دوطرفه برای همهٔ رویدادهای عضویت با لینک عمیق. ✅
7. 🔨 **تامین‌کننده‌ای که درخواستش رد شد**، دیگر هیچ نشانی نداشت → در «درخواستهای قیمت» بخش
   «درخواست رد شده» با دکمهٔ حذف اضافه می‌شود. (بک: `requests` شامل `declined` هم می‌شود.)

## فاز ۴ — قیمت‌گیری (تامین‌کننده)
1. تب «درخواستهای قیمت»: بازوهای خریدی که تامین‌کنندهٔ تاییدشده‌شان است + اقلام فوری + «مهلت ارسال قیمت: ۱۲:۳۰ ساعت». ✅
2. ثبت پیشنهاد برای **هر قلم** یا **کل لیست**: «انتخاب واحد» (پیش‌انتخاب واحد قلم، جست‌جودار) ←
   «قیمت پیشنهادی برای هر کارتن» (تومان، سه‌رقمی) ← زمان تحویل (روز) ← مزیت خرید ← پیام. ✅
   شمارهٔ تماس = موبایل ثبت‌نام (خودکار، بدون ورود). ✅
3. چرخهٔ وضعیت پیشنهاد: «ارسال شده» (قابل ویرایش تا تصمیم خریدار) → تایید/رد → قفل. ✅
4. 🔨 **انصراف از پیشنهاد** (`withdrawn`) — بک آماده بود، دکمه به کارت «ارسال شده» اضافه می‌شود.
5. 🔨 **گیت مهلت/توقف در سرنخ‌ها**: با تمام‌شدن مهلت یا «توقف قیمت‌گیری» خریدار، دکمهٔ «پیشنهاد قیمت»
   غیرفعال می‌شود (قبلاً فقط متن عوض می‌شد). پیشنهادهای قبلی همچنان قابل ویرایش‌اند.
6. بازوی متوقف‌شده (توقف موقت) در سرنخ‌ها با برچسب «توقف موقت قیمت‌گیری» دیده می‌شود اما پیشنهاد جدید نمی‌گیرد؛
   بازوی بسته‌شدهٔ نهایی (پرونده) کلاً از سرنخ‌ها خارج می‌شود. 🔨 (بک: فلگ `paused`)

## فاز ۵ — تصمیم خریدار (پیشنهادها)
1. کارت هر پیشنهاد: فروشنده، قیمت + مبنا، قلم، تحویل، مزیت، پیام، **دکمهٔ تماس**. ✅
2. **پذیرش ۱ تا ۳ پیشنهاد برای مذاکرهٔ نهایی** — پذیرش‌ها مستقل‌اند (یک لیست خرید لزماً یک برنده ندارد؛
   ممکن است هر قلم تامین‌کنندهٔ جدا داشته باشد). ✅
3. 🔨 **بخش «پذیرفته‌شده‌ها — مذاکرهٔ نهایی»** بالای تب پیشنهادها: خیلی جلو چشم، با بج نتیجهٔ فروش
   («فروش نهایی شد» / «فروش نهایی نشد» / «نتیجه ثبت نشده») که تامین‌کننده ثبت می‌کند.
4. رد پیشنهادها؛ پیشنهاد ردشده قفل است. ✅
5. بعد از پذیرش، ویرایش پیشنهاد قفل است — **مذاکرهٔ نهایی بیرون از آی مچ و با تماس** انجام می‌شود. ✅

## فاز ۶ — پایان معامله و بستن پرونده
1. طرفین مذاکره را با تماس تمام می‌کنند؛ تامین‌کننده نتیجه را ثبت می‌کند: «فروش نهایی شد / نشد». ✅
2. 🔨 **بستن پروندهٔ بازوی خرید (خریدار)** — دکمهٔ «بستن پرونده» در تب پیشنهادها:
   - دو گزینهٔ بزرگ: **«معامله انجام شد (موفق)»** / **«به نتیجه نرسید (ناموفق)»**
   - با بستن پرونده: پیشنهادهای بدون تصمیم «رد شده» می‌شوند (تکلیف روشن) + اعلان به همهٔ طرفین
   - بازو `archived` می‌شود: از لیست عمومی، بازار و درخواستهای قیمت حذف می‌شود (فقط مالک از پنل می‌بیند)
3. 🔨 **بخش «پرونده‌های بسته‌شده»** در پنل خریدار (فیلتر آرشیو): کارت با نتیجهٔ معامله (موفق/ناموفق)
   و امکان «بازکردن دوبارهٔ پرونده» در صورت اشتباه.
4. مبنای گزارش‌های آیندهٔ فروش (owner/admin): `saleStatus` + `outcome` روی همین داده‌ها سوار است. ⏳

## فاز ۷ — قواعد مشترک (همهٔ فازها)

- شمارهٔ پیشنهاددهنده هرگز در فرم وارد نمی‌شود (ضد نشت). ✅
- شناسه‌های خالی هرگز ۵۰۰ نمی‌دهند (sanitize). ✅
- همهٔ فرم‌ها: `toastFormErrors` + NumberInput سه‌رقمی + Select جست‌جودار + تاریخ/ساعت فارسی. ✅
